# Miracle — бриф на контракты

Документ для агента, который пишет смарт-контракты. Фронтенд делает другой агент; здесь зафиксировано, кто что делает и как две части стыкуются.

**Приоритет — скорость.** Всё, что можно не делать, ниже помечено явно. Обязательного мало, и оно всё про деньги.

---

## 1. Что за продукт

Miracle — турнир по торговле на Robinhood Chain.

- Игрок платит реальный взнос в ETH, взнос уходит в призовой фонд сезона.
- Внутри сезона у всех **одинаковый виртуальный торговый капитал**. Размер кошелька не даёт преимущества.
- Игрок открывает и закрывает позиции по активам, у которых есть фид Chainlink. Позиции виртуальные, исполнения на рынке нет.
- В конце сезона участники ранжируются по итоговому капиталу, призовой фонд делится по правилам, зашитым в контракт.
- Плечо от 3× до 10× зависит от счёта, накопленного в прошлых сезонах.

Продуктовое обещание: всё состояние игры лежит в контракте, цены берутся из Chainlink, лидерборд не может отредактировать никто, включая владельца. Сервера, который считает деньги, в системе нет.

## 6. Фиксированная точка — согласовать точно

Самое вероятное место расхождения с фронтендом. Договорённость:

| Величина | Представление |
|---|---|
| Риск-вес | `uint16` в bps: `10000` = 1.0×. SGOV `5000`, SPY `10000`, MSTR `25000` |
| Плечо | `uint32` в bps: 3× = `30000`, 10× = `100000` |
| Счёт игрока | `uint16`, диапазон 0…100 |
| Капитал, номинал, эквити | `uint256`, масштаб **1e18** (WAD) |
| Цена из фида | как отдал фид (8 знаков), в библиотеке нормализуется в 1e18 |

Формула плеча в целых числах:

```
leverageBps = 30000 + score * 700        // score 0..100  →  30000..100000
```

Проверка: `score = 0` → `30000` (3×). `score = 100` → `100000` (10×). Совпадает с `leverageFromScore` в `formulas.ts`.

Остальное:

```
aumCapacity      = capital * leverageBps / 10000
riskWeightedAum  = Σ (notional * riskWeightBps / 10000)
capitalAdequate  = riskWeightedAum <= aumCapacity
pnl              = notional * (currentPrice - entryPrice) / entryPrice     // long
                   с обратным знаком для short
```

## 7. Два механизма, которые нужно сделать правильно

Всё остальное в контракте — обычный учёт. Эти два — нет.

### 7.1 Цена входа — следующий раунд оракула

**Зачем.** Если цена входа берётся в момент транзакции, игрок с более быстрым прайс-фидом видит движение раньше сети и открывает позицию по заведомо устаревшей цене. На дистанции он системно выносит призовой фонд. Это не теория, это стандартная атака на симуляторы со ставками.

**Как.** В `openPosition` не читаем цену вообще. Пишем только `openedAt = block.timestamp`.

Цена входа определяется позже, при закрытии или расчёте. Вызывающий передаёт подсказку `entryRoundHint`, контракт проверяет, что это **первый раунд после открытия**:

```
getRoundData(hint).updatedAt     >= openedAt
getRoundData(hint - 1).updatedAt <  openedAt
```

Обе проверки обязательны — одна без другой позволяет подсунуть любой более поздний выгодный раунд. Проверка O(1), подделать нельзя.

**Мина.** В прокси Chainlink `roundId` кодирует `phaseId` в старших 64 битах, поэтому `hint - 1` на границе фаз указывает в пустоту и вернёт мусор или ревертнет. Обрабатывай смену фазы явно и покрой тестом — это самое неочевидное место во всём контракте.

### 7.2 Рейтинг — контракт проверяет, а не сортирует

**Зачем.** Сортировать тысячу участников ончейн дорого и незачем.

**Как.** `submitRanking` принимает готовый отсортированный массив адресов. Любой желающий считает порядок офчейн и подаёт его. Контракт за один проход проверяет:

1. длина массива равна числу участников сезона;
2. эквити невозрастающее вдоль массива (`equityOf(ordered[i]) >= equityOf(ordered[i+1])`);
3. **дубликатов нет** — иначе подают массив из одного победителя много раз;
4. сезон в фазе расчёта.

Проверка линейная, доверия ни к кому не требует. Первая валидная подача принимается.

Для дубликатов: при входе в сезон выдавай игроку индекс, в `submitRanking` отмечай индексы битмапой. Так проверка остаётся за один проход без вложенных циклов.

### 7.3 Валидация фида

В библиотеке, на каждом чтении:

```
answer > 0
answeredInRound >= roundId
block.timestamp - updatedAt <= heartbeat
```

**Важно про акции.** Фиды акций работают 24/5 и вне торговых часов просто держат последнюю цену, **не публикуя heartbeat**. Проверки `answer > 0` категорически недостаточно: без контроля `updatedAt` контракт всё выходные будет торговать пятничной ценой закрытия. У всех восьми наших фидов heartbeat = 86400 секунд.

## 8. Что пропускаем ради скорости

Не делай ничего из этого, если специально не попросят:

- **Апгрейдабельность и прокси.** Контракт неизменяемый. Нужна новая версия — деплоим заново. Прокси добавляют и время, и класс уязвимостей.
- **Мультисиг и управление.** Один ключ владельца на v1.
- **Оптимизация газа.** Транзакция стоит сотые доли цента. Читаемость важнее.
- **Отдельный контракт реестра цен.** Маппинг `symbol → feed` живёт внутри `MiracleGame`.
- **Индексер и сабграф.** Фронтенд читает контракт напрямую батчем.
- **CI, линтеры, пороги покрытия, natspec на каждой функции, slither/mythril как гейт.** Хочешь прогнать — прогони, но не блокируйся.
- **Формальная верификация.**
- **Фаззинг и инвариантные тесты всего подряд.** Только то, что в разделе 9.
- **События сверх необходимого.** Нужны только те, что перечислены в разделе 10.
- **Пауза, блокировки, лимиты, whitelist.** На v1 не нужны.

Деплой сразу в тестнет и итерируй там. Не строй локальный стенд, если тестнет быстрее.

## 9. Что пропускать нельзя

Три пункта. Все про то, что в контракте лежат чужие деньги.

1. **Защита от реентранси на `claim`.** Выплата отправляет ETH внешнему адресу. Списывай долг до отправки (checks-effects-interactions) либо ставь guard. Это единственная необратимая уязвимость в системе: она уносит весь пул разом.

2. **Тесты денежных путей.** Ровно четыре: `joinSeason` учитывает взнос; `submitRanking` отклоняет неверный порядок и дубликаты; `claim` платит правильную сумму; `claim` нельзя вызвать дважды. Плюс один инвариант: **сумма всех выплат сезона никогда не превышает собранный фонд**. Больше не нужно.

3. **Аудит перед мейннетом с реальным призовым фондом.** На тестнете — не нужен, гоняй свободно. Порог ровно там, где появляются настоящие деньги.

## 12. Изменения границы со стороны фронтенда

Журнал правок `packages/shared/src/types.ts` — по п. 2 их нельзя вносить молча.

### 2026-09-16 — `SeasonState` получил три поля

```ts
readonly maxParticipants: number;
readonly feeBps: number;
readonly payoutBps: readonly number[];
```

Все три уже возвращает `getSeason` в `SeasonView`, так что реальному адаптеру их брать неоткуда, кроме как оттуда — новых вызовов не появляется.

Зачем: страница лидерборда показывает, сколько платит каждое место. Без кривой из сезона проценты пришлось бы вписать в вёрстку, и они разошлись бы с любым сезоном, созданным с другой кривой.

Рядом появился `packages/shared/src/payouts.ts` — `platformFee`, `placePrizes`, `seasonPlaces`, повторяющие `_distribute` и `_placePrizes` из `MiracleGame.sol`, включая деление призов внутри группы с равным эквити. 14 тестов. Если логика выплат в контракте меняется, эти функции нужно менять вместе с ней.

### 2026-09-16 — `Position` получил состояние закрытия, `LeaderboardEntry.equity` стал точным

```ts
export type PositionStatus = "open" | "closing" | "settled";
// Position: + status, closedAt, exitPrice, exitRoundId, pnl, voided
// LeaderboardEntry.equity: number → bigint (WAD)
```

`equity` — bigint, потому что ничью контракт определяет точным сравнением `uint256`, а игроки в ничьей делят призы своих мест. Два эквити, различные на чейне, после округления в `number` совпадают — превью выплат показало бы обоим не ту сумму. `seasonPlaces` теперь принимает `bigint[]`; есть тест на разницу в 1 wei.

Рядом появился `packages/shared/src/units.ts` — `toWad` / `fromWad` (12 тестов). `toWad` идёт через кратчайшее десятичное представление, а не через умножение: `0.1 * 1e18` в double даёт `100000000000000005`. Перевод в `number` происходит только в момент вывода на экран.

Мок-адаптер приведён к двухшаговому закрытию: `closePosition` пишет только `closedAt`, результат появляется на следующей котировке. Позиция в статусе `closing` продолжает занимать ёмкость, как в контракте.

### 2026-09-16 — расчёт позиций вынесен в интерфейс

```ts
export interface SettlementHint {
  readonly positionId: string;
  readonly entryRoundId: bigint;
  readonly exitRoundId: bigint;
}
// MiracleAdapter: + getSettlements(seasonId, address)
//                 + settlePositions(seasonId, address, hints)
```

Кипер запускает владелец вручную, сервера у нас нет. Без этого закрытая позиция висела бы в `closing` и держала ёмкость до следующего запуска кипера, а игрок не видел бы PnL. Теперь игрок рассчитывает свои позиции сам: фронт ищет подсказки через `findFirstRoundAfter` и шлёт пакетный `settlePositions` (пакетный, а не одиночный, — он пропускает уже рассчитанные, а одиночный ревертит `PositionAlreadySettled`, и гонка с кипером тут штатная).

`now` для поиска берётся из `getBlock().timestamp`, а не из часов браузера: аннулирование мёртвого фида контракт считает по времени блока. Адреса фидов читаются из `getAssets()`, а не из `assets.ts`, — источником истины остаётся контракт. Раунды кэшируются: они неизменяемы, а один поиск стоит 11–13 чтений.

Мок тоже переведён на явный расчёт: раньше он книжил PnL сам на следующей котировке и прятал шаг, который на чейне игроку придётся сделать руками.
